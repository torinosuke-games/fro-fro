# Claude Code への引き継ぎ — 雪山フィールドの独立試作

## 境界とレビュー対象

`codex-prototypes/snowfield-canvas/` だけが追加対象です。既存のゲーム・仕様・判断記録・テスト・画像は変更していません。自動保存・Supabase・FF.app・ゲーム本体のスクリプトに接続していません。commit・push・本体への組み込みは未実施です。

この試作はフィールドの描画と操作の評価用です。戦闘、敵、報酬、実際の回復、編成、解放判定、セーブは接続していません。「旅の仲間4人」は表示用で、フィールド上は主人公1人です。施設操作は案内文だけです。物語上の新しい確定仕様にはしないでください。

## 採用候補

- 地面を傾けるCSS 3Dから、Canvas 2Dによる斜め見下ろし描画へ。地面・遠景・立体物の素材を分離。
- 生成画像の木・家・岩を足元Y順で並べ、主人公を挟む。隠れる場合は手前の立体物だけ薄くする。
- 地形・道・崖・雪面は一度だけCanvasに焼き込む。画面外の立体物は描かない。
- スマホ幅600px以下は初期状態から低解像度（DPR 1）・最大約30描画/秒。標準はDPR 1.5上限。自動の標準状態では、連続して遅い場合に軽量へ落とす。
- 静止後はrequestAnimationFrameを終了。タブが隠れたときも停止。方向入力解除・フォーカス喪失・pointercancelに対応。
- 中央の8方向パッド、地面タップ、全体マップの目的地選択。横画面はパッドを左へ移し、主人公の表示領域を確保。
- `prefers-reduced-motion` では歩行の上下動とカメラの遅れを抑える。

## 本体へ接続する場合

1. `MAP`と`PLACES`は現行 `js/adventure.js` と同じスナップショットです。採用時には同じ定義を参照させ、二重管理を解消してください。
2. `begin`/`frame`は試作用の連続補間です。本体ではマス移動の確定を **既存の A.move とイベント処理** に渡してください。試作の座標をそのままFF.appへ代入してはいけません。
3. 斜め移動の条件は横・縦の両隣が通れることです。既存実装は斜めの途中で各マスの戦闘・宝箱・焚き火等が発生します。既存のイベント順序を維持してください。
4. 峠のボス・通行解放・ランダム戦闘はこの試作にありません。本体のゲーム進行を優先し、そのロジックから描画へ状態を渡してください。
5. 入力と見た目の補間を分離し、到着・イベント時の保存ルールを維持してください。visibilitychangeでの試作の丸め戻しは、本体の確定済み論理座標を参照する方式へ置き換えてください。
6. 施設は通行可能な目的地の北側へ少しずらして表示しています。入口と操作位置が一致するか実際のゲーム画面で確認してください。
7. 既存のアバター選択を使う場合は全14シートのランタイム縮小版の生成が別途必要です。本試作はe1のみです。
8. UI文言・ふりがな・テーマ変数は採用時に本体の管理方法へ統合してください。
9. 地図のスクリーンリーダー操作は施設ボタンと4方向のキーボード操作で補っていますが、非視覚での探索全体の案内は未完成です。

## 評価の反復

- 1回目：独立ページ、4素材アトラス＋遠景、既存主人公、移動操作を実装。写真記録は `qa/*-v1.png`。
- 自己評価：雪面が均一、崖が板状、画面端の構図が偏る、横画面でパッドが主人公を隠す。
- 2回目：生成した雪テクスチャ、岩による崖、接地影、カメラ端の制限、横画面配置を修正。
- 負荷評価：CPU4倍スロットル時に自動画質判定が遅く、dt上限で移動が遅くなった。判定を90から24サンプルへ短縮、dt上限を調整し、スマホでは最初から軽量に変更。
- 3回目：宝箱・焚き火も生成素材へ。最終スクリーンショットと操作テストを再実行。

## 残る制約・実機で確認したい点

- 本格的な3D地形・パース投影ではなく、固定の斜め見下ろしと絵の重なりによる表現です。建物の裏側へ回る視点変更はありません。
- 木が同じ素材なので林には反復感があります。主な通路は認識できますが、林の縁の視認性は実機で確認してください。
- iOS Safari・Android実機の熱・電池・入力遅延は未測定。Linux Chromiumのソフトウェア描画・CPUスロットルを、スマホの実測FPSとは扱わないでください。
- 採用判断前に、一般的なAndroidとiPhoneで各5分の連続移動、画面回転、タブ切り替え、地図操作を確認するとよいです。実機で30fpsを下回る場合は、カメラ移動中の近景キャッシュやキャラクター用Canvasの分離を検討してください。

## 同条件の比較結果

最終比較（`qa/benchmark.json`）は現行ページと試作ページを別々に読み込み、390×844・DPR3・CPU4倍スロットルで、同じパッドの東西操作を行っています。

|指標|現行HD-2D|試作・スマホ自動|
|---|---:|---:|
|独立RAFプローブの待ち時間中央値|83.3ms|16.7ms|
|同95パーセンタイル|150ms|16.8ms|
|同50ms超の回数|55|0|
|計測区間のレイアウト回数|8|3|
|ページ全体のDOM数|437|72|

RAFプローブはブラウザーの応答性の参考であり、試作は30描画/秒に制限しているため「試作60fps」という意味ではありません。また、計測区間のScriptDuration / TaskDurationは試作のほうが大きく、総CPU時間や消費電力が減ったとまでは結論できません。ページ全体の機能数も異なります。実機では発熱・電池・入力遅延も含めて評価してください。

最終の目視確認で、タイトルと目的地欄の間隔、および施設到着時に焚き火と主人公が重ならない配置も調整しました。
